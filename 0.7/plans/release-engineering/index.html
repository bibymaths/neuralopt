Disagreements and notes¶

  1. Dates depend on the time zone.
  2. The dates you supplied are the merge commits' local dates (+05:30).
  3. GitHub shows merge times in UTC, and on that basis four versions merged one day earlier:
    • v0.1.0: 11-14, not 11-15;
    • v0.4.0: 11-15, not 11-16;
    • v0.5.0: 11-20, not 11-21;
    • v0.6.0: 11-21, not 11-22.
  4. D1, decided: UTC dates everywhere (GitHub's merge dates). These go in the CHANGELOG, the release notes and the tag messages. Each tag message also gives the +05:30 local merge time.
  5. The dates are therefore:
    • v0.1.0: 2026-11-14;
    • v0.2.0: 2026-11-15;
    • v0.3.0: 2026-11-15;
    • v0.4.0: 2026-11-15;

  6. The version number at the v0.6.0 commit is wrong. At bef56bc, pyproject.toml, __init__.__version__ and CITATION.cff all say 0.5.0.
  7. The tag is still correct: the CHANGELOG and the PR both describe v0.6.
  8. However, a wheel built from it would be named neuralopt-0.5.0. See D2 in item 6.
  9. Every old tag carries a zensical.toml. That makes the docs backfill (item 7) feasible for all six old versions.

  • vX.Y.Z.md for 0.1.0 through 0.7.0, plus an index.md table with one row per version: version, date, one-line summary, and result type (infrastructure / positive / negative).
  • Sources: CHANGELOG entries, the version's research reports (mapped below) and the PR commit lists. Reports are linked, not rewritten.
  • Sections: Highlights, Features, Research results, Fixes, Documentation, Build and CI, Breaking changes, and Known limitations. Empty sections are written as "None."
  • Research results state the outcome in the first sentence. For example: "Negative: learned geometry did not beat the validation-tuned fixed diagonal."

4. git-cliff and conventional commits¶

  • cliff.toml will be replaced with a copy of the globax configuration:
  • conventional_commits = true and filter_unconventional = false;
  • the same emoji groups and commit preprocessors;
  • tag_pattern = "v[0-9].*";
  • links rewritten to bibymaths/neuralopt.
  • git-cliff only drafts. A new scripts/draft_release_notes.sh vX.Y.Z runs git cliff --unreleased --tag vX.Y.Z and writes to stdout or a scratch file. It never writes CHANGELOG.md or a docs/release-notes/ file. Unlike globax, there is no changelog workflow that rewrites CHANGELOG.md.
  • Release procedure (in CONTRIBUTING.md):
  • Draft the notes with git-cliff.
  • Curate them into docs/release-notes/vX.Y.Z.md.
  • Prepend a CHANGELOG section.
  • Bump the version.
  • Open a PR, then merge it.
  • Tag the merge commit.
  • CONTRIBUTING.md gains:
  • the commit types (feat fix docs perf refactor test build ci chore revert, plus research → grouped under "Research", a NeuralOpt addition);
  • the scope convention;
  • a ! / BREAKING CHANGE: footer for breaking changes;
  • the release procedure.
  • PR-title check: .github/workflows/pr-title.yml, using amannn/action-semantic-pull-request pinned to a release tag, with pull-requests: read only. It runs on pull_request (not pull_request_target), so fork code never gets elevated permissions.
  • History is not rewritten. Old commits stay unconventional; git-cliff groups them under "Other".
  • D3, decided: squash-merge with the PR title as the commit message. You set it in Settings. With that setting, the PR-title check guarantees conventional commits on main. CONTRIBUTING.md documents this.

5. Version metadata: a single source¶

  • pyproject.toml is the source of truth (version = "0.7.0").
  • neuralopt.__version__ = importlib.metadata.version("neuralopt").
  • .bumpversion.toml is deleted: it is stale, and nothing uses it.
  • CITATION.cff (version and date-released) is set in the release PR, as step 4 of the release procedure (item 4).
  • .zenodo.json omits version, so Zenodo takes it from the release tag. That leaves one less field to keep in sync.
  • scripts/check_release.py vX.Y.Z verifies that:
  • the tag, pyproject.toml's version and CITATION.cff's version are all equal;
  • if .zenodo.json ever gains a version, it must equal the tag too;
  • CITATION.cff's date-released equals the date of this version's CHANGELOG heading;
  • CITATION.cff passes cffconvert --validate, run in CI as uvx cffconvert==2.0.0 --validate. It stays out of the project's dependencies, because it pins old jsonschema versions;
  • .zenodo.json is valid JSON with the required keys: title, upload_type, description, creators, license, access_right and related_identifiers;
  • docs/release-notes/vX.Y.Z.md exists;
  • CHANGELOG.md has a ## [X.Y.Z] - heading.
  • The metadata checks also run in ci.yml, on every PR: cffconvert --validate, plus check_release.py --metadata-only for the JSON and the version agreement.
  • With --backfill, it skips the three-way version check (D2) and checks only that the notes and the CHANGELOG entry exist on main.
  • Tests:
  • __version__ matches pyproject.toml;
  • the release checker passes on 0.7.0;
  • the release checker fails when a version mismatches, a notes file is missing, the date-released disagrees with the CHANGELOG, or .zenodo.json is invalid.

6. .github/workflows/release.yml¶

Triggers: - push: tags: ['v*']; - workflow_dispatch with inputs tag (string) and publish_pypi (boolean, default false), used for backfill.

Workflow-level settings: - permissions: contents: read; - concurrency: release-${{ tag }} with cancel-in-progress: false.

Jobs:

  1. verify checks out ref: <tag> and runs check_release.py. For tags below v0.7.0, it runs --backfill against main's files.
  2. Outputs: version, is_backfill, and pypi_ok. pypi_ok is true when Version(tag) >= 0.7.0 and either the run was a tag push or publish_pypi is true. The comparison uses packaging.version.
  3. test runs the full quality gate at the tag: uv sync --extra dev --extra docs, ruff check ., pyright, pytest -q, zensical build --strict, uv build, and twine check dist/*.
  4. It is skipped for backfill, because those commits passed CI in their own PRs and old tags lack the current tooling. The release notes say so.
  5. build runs uv build at the tag and uploads dist/ with actions/upload-artifact and retention-days: 3.
  6. D2, decided: v0.6.0 gets no build files. Its sdist and wheel would be named 0.5.0, so build is skipped for v0.6.0. Its release notes explain why. All other versions get both an sdist and a wheel.
  7. pypi has needs: [verify, test, build] and if: pypi_ok.
  8. environment: pypi, and permissions: id-token: write in this job only.
  9. It uses pypa/gh-action-pypi-publish pinned to a release tag. That is trusted publishing, with no tokens.
  10. github-release has permissions: contents: write.
  11. It uses gh release create vX.Y.Z --title "NeuralOpt vX.Y.Z" --notes-file docs/release-notes/vX.Y.Z.md --prerelease --verify-tag, then attaches the dist files.
  12. The notes file is read from main for backfill. All 0.x releases are marked as pre-releases.
  13. For backfill it waits for nothing on PyPI. For v0.7.0 it runs after pypi succeeds.
  14. docs calls the reusable deploy steps from item 7 for the tag's minor version.
  15. It runs in concurrency: gh-pages (shared with docs.yml, cancel-in-progress: false), so deploys never overlap.

Common to all jobs: - Actions are pinned to full release tags: actions/checkout@v4.x.y, astral-sh/setup-uv@v6.x.y, and so on, with exact values resolved in Phase 2. - Option: pin to commit SHAs instead. That is safer but noisier, so say if you want it. - No other workflow uploads artifacts. Release files live only on the GitHub release.

7. Versioned docs (Zensical plus its mike fork)¶

Tooling: - Zensical's versioning is a temporary fork of mike 2.2.0 (squidfunk/mike). It is not on PyPI. - It is installed from git, pinned to a commit hash: mike @ git+https://github.com/squidfunk/mike@2d4ad799442f4592db8ad53b179bfb33db8c69ac. - That is the head of master on 2026-04-17. The fork of jimporter/mike was last pushed on 2026-10-11. - It is used in the docs extra and in the workflows. - The zensical.toml setting is [project.extra.version] provider = "mike", with alias = true and default = "latest". - What I read in the fork at that commit: - Zensical version: it requires zensical >= 0.0.30. The installed 0.1.1 satisfies that, so Zensical is not upgraded. If Phase 2 nonetheless shows an incompatibility, Zensical is upgraded and zensical build --strict is run again. - How it builds: mike deploy runs zensical build --clean, without --strict. Strictness is therefore a separate zensical build --strict step, run before every deploy. - Config file: mike reads zensical.toml, or the file given with -F/--config-file. It resolves site_dir relative to that file's directory. - Commands: mike 2.2.0's (deploy --push --update-aliases, set-default, list, -b gh-pages). - The Zensical versioning page (zensical.org/docs/setup/versioning/) currently redirects to a 404. The fork's README points to the upstream mike documentation.

Layout on gh-pages: - one folder per minor version, 0.1/ … 0.7/, each titled with its full version (for example "0.7.0"); - aliases latest (the newest release) and dev (main); - mike set-default latest; - site_url = https://bibymaths.github.io/neuralopt/.

.github/workflows/docs.yml: - On PRs it runs zensical build --strict only, with no deploy. - On pushes to main it runs mike deploy --push --update-aliases dev. - It runs in concurrency group gh-pages, with permissions: contents: write only in the deploy job.

Backfill (scripts/backfill_docs.py): for each old tag it: 1. runs git worktree add <tmp> vX.Y.0; 2. writes an untracked overlay config at the worktree root: the tag's zensical.toml plus site_url and the version provider. It is named .zensical-versioned.toml and passed with -F. It has to sit at the root, because docs_dir and site_dir resolve relative to the config file. It is never committed, and the worktree is deleted afterwards. 3. runs mike deploy --config-file <overlay> 0.N with --title 0.N.0; 4. runs zensical build --strict -f <overlay> first. If that fails, it records the failure and deploys anyway, since mike's own build is non-strict; 5. removes the worktree.

The script: - writes a report to artifacts/docs-backfill-report.json (gitignored scratch, not a workflow artifact) listing strict, non-strict and failed builds; - defaults to --no-push (a local gh-pages commit only). Pushing needs --push and happens only in Phase 3, after you approve.

Phase 2 local check: build two versions (0.6 and 0.7) into a local gh-pages with mike deploy (no push), then mike serve and check the version selector. The result is reported.
